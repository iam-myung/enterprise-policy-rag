# 企业内部制度知识库问答系统 PRD

| 项目属性 | 内容 |
| --- | --- |
| 版本 | v1.0 |
| 项目模式 | 非商业 / 个人独立开发项目 |
| 当前阶段 | Phase 1（MVP） |
| 项目目标 | 完成可运行、可评测、可演示的独立开发项目，证明制度类 RAG 项目的完整设计与交付能力。 |
| 文档目的 | 明确产品价值、MVP 边界、验收标准与后续阶段，供架构与开发阶段使用。 |

## 0. 需求验证

### 0.1 核心判断

**结论：值得做，但 v1 仅验证“能否快速、可信地找到制度答案”。**

企业新员工、跨部门协作人员在查找报销、考勤、请假、审批等制度时，常面临文件分散、关键词不一致、答案缺少出处的问题。普通文件夹搜索只能返回文件或片段，无法直接给出带依据的可用结论；通用大模型则可能生成没有制度依据的回答。

本项目的差异不在于“做一个聊天框”，而在于让用户获得**基于指定制度文档、可回看原文页码的答案**。若没有真实制度语料，v1 可先使用脱敏或公开制度样例验证闭环，但不得把演示数据表述为真实企业数据。

### 0.2 7 天验证目标

- 使用至少 3 份结构清晰的制度 PDF 建立知识库，首批覆盖考勤、请假和报销场景。
- 准备至少 20 个测试问题，覆盖直接查询、跨段落查询、无答案查询和制度冲突查询。
- 邀请至少 3 名目标用户完成各自 1 次真实或模拟查询。
- 所有正常回答均应展示可定位的原文依据；对无依据问题应明确说明“制度库未找到依据”。
- 以“纯向量检索”为基线，对比混合检索与重排方案的检索和回答质量，不预设未经实测的提升比例。

## 1. 产品定位

**一句话定位：** 面向需要快速了解公司规则的新员工，提供基于现行制度、带原文依据的问答结果，减少人工翻找和错误理解。

### 1.1 版本定义

- **v1 = Phase 1 MVP：** 制度维护者导入考勤、请假和报销制度 PDF，新员工输入问题后获得基于现行制度、带明确来源的答案。
- **v1 不承诺：** 覆盖全公司知识、替代 HR/法务解释，或处理需要人工审批的制度例外。

### 1.2 首批内容范围

| 范围 | v1 约束 |
| --- | --- |
| 制度类型 | 考勤、请假、报销三类公开或脱敏制度样例。 |
| 文档要求 | 文件需具有清晰标题、正文和页码，并补充版本、生效日期与适用范围；缺少的信息应标记为“待确认”。 |
| 数据声明 | 演示数据不得表述为真实企业内部数据，作品说明需明确其为公开或脱敏样例。 |

## 2. 用户与痛点

| 用户角色 | 典型场景 | 核心痛点 |
| --- | --- | --- |
| 新员工（核心用户） | 查询考勤、请假和报销规则 | 不知道制度文件在哪里，也难判断搜到的段落是否为现行规定、是否适用于自己。 |
| 制度维护者（辅助用户） | 导入和更新制度资料 | 难以确认资料是否生效、重复、过期或存在冲突。 |
| 跨部门员工（后续用户） | 查询采购、协作和审批规则 | 需求成立，但不进入 v1 首批验证范围。 |

## 3. MVP 范围

### 3.1 Phase 1（v1）

| 优先级 | 功能 | 用户价值 | 复杂度 |
| --- | --- | --- | --- |
| P0 | 制度文档导入与解析 | 将指定 PDF 制度文档转为可检索知识，保留文档名与页码信息。 | 🟡 |
| P0 | 带引用的制度问答 | 输入自然语言问题，返回简明答案、引用片段及原文页码/定位信息。 | 🟡 |
| P0 | 回答质量验证 | 对预设问题集执行基础评测，记录回答、引用与失败样本，支持后续优化。 | 🟡 |
| P1 | 知识库健康度检查 | 识别疑似过期、缺失或冲突的制度内容。 | 🟡 |
| P1 | 知识库版本对比 | 对比更新前后的制度知识库与检索表现。 | 🟡 |
| P1 | 问题反馈 | 用户可标记“有帮助 / 未解决”，沉淀优化样本。 | 🟢 |
| 🚫 禁止进入 v1 | 登录、多角色权限、部门隔离、审批流、在线编辑制度、多知识库协同、移动端、复杂数据看板 | 不能直接验证“可信制度问答”的核心价值。 | - |

### 3.2 产品规则

1. 回答必须基于已导入的制度资料；缺少证据时，系统应说明未找到依据，而非补全猜测。
2. 制度资料需保留文件名、版本、生效日期、适用范围与来源；缺失字段应显示“待确认”，不得自动推断。
3. 默认回答优先采用已确认的现行版本；已废止或失效制度不得作为默认答案依据。
4. 多份现行制度出现冲突时，系统不得自行裁决，应同时展示冲突依据并提示制度维护者确认。
5. 每个正常回答至少展示一条可追溯来源，包含制度文件名、页码/定位和支持答案的原文片段。
6. 用户应能区分“系统回答”和“制度原文依据”，不得将模型生成内容伪装成原文。
7. 制度解释仅供检索辅助；涉及例外、争议或未覆盖事项时，应提示用户向制度维护者确认。

## 4. 核心用户流程

### 4.1 业务闭环

```text
制度 PDF 导入
  → 文档解析与切片
  → 建立知识库
  → 员工输入问题
  → 混合检索与相关内容筛选
  → 生成答案 + 原文引用
  → 用户核对原文
  → 测试集与失败样本用于下一轮优化
```

### 4.2 页面与交互要求

| 页面/区域 | 目标 | 关键内容 | 成功标准 |
| --- | --- | --- | --- |
| 制度问答页 | 让用户快速获得可信答案 | 问题输入、答案、制度版本提示、引用原文、原文回看入口 | 用户可在一次查询中看懂答案并核对依据。 |
| 文档处理状态区（维护者） | 确认哪些资料进入知识库 | 文档名称、版本/生效状态、处理状态、页数与失败原因 | 维护者能判断文档是否可查询；v1 不要求独立管理后台。 |
| 评测结果输出（项目维护者） | 判断系统是否可靠 | 测试问题、标准依据、回答、引用、指标与失败原因 | 可定位错误属于解析、检索、生成或引用问题；v1 不要求独立评测页面。 |

## 5. 需求与验收标准

### 5.1 P0-1：制度文档导入与解析

**用户故事：** 作为制度维护者，我希望导入一份 PDF 制度文件并确认其已被处理，以便员工可以查询其中的规则。

| 场景 | 验收标准 |
| --- | --- |
| 正常流程 | 导入有效 PDF 并补充版本、生效日期、适用范围后，系统显示处理完成状态、文件名和可用于引用的页码信息。 |
| 解析失败 | 文件无法读取、内容为空或解析失败时，系统展示明确失败原因，不将该文件标记为可查询。 |
| 边界情况 | 重复导入时提示重复或更新；失效版本不进入默认问答；元数据缺失时标记“待确认”。 |

### 5.2 P0-2：带引用的制度问答

**用户故事：** 作为员工，我希望用自然语言提问并查看答案依据，以便快速确认制度规则而不是凭印象执行。

| 场景 | 验收标准 |
| --- | --- |
| 正常流程 | 对知识库覆盖的问题，系统返回简明答案，并展示制度文件名、版本/生效信息、页码/定位及支持答案的原文片段；用户可从引用回看对应原文。 |
| 无依据问题 | 未检索到足够证据时，系统明确说明未找到制度依据，并建议用户更换关键词或咨询制度维护者。 |
| 边界情况 | 多份现行制度冲突时同时展示相关依据并提示人工确认；连续提交、空问题、问题过长或模型服务异常时展示明确状态。 |

### 5.3 P0-3：回答质量验证

**用户故事：** 作为项目维护者，我希望用固定问题集复核回答质量，以便知道系统是否真的可靠。

| 场景 | 验收标准 |
| --- | --- |
| 正常流程 | 对固定测试集分别运行基线方案与目标方案，生成可查看的回答、引用、检索指标与回答质量记录。 |
| 失败样本 | 回答错误、未引用或引用不相关时，可保留问题、答案和失败原因供优化。 |
| 边界情况 | 测试集缺少标准依据、制度版本变更或指标无法计算时，结果应标记为待复核，而非直接判定通过。 |

## 6. 分阶段交付与责任边界

| 阶段 | 目标 | Owner | 输出物 |
| --- | --- | --- | --- |
| Phase 1 | 完成“导入制度 → 提问 → 带引用回答 → 评测”的最小闭环 | 产品经理、系统架构师、LLM 后端、前端、QA | PRD、架构 SPEC、可运行 Demo、20+ 问题测试集、基线对比评测报告、失败案例、演示截图/录屏与项目说明。 |
| Phase 2 | 提升资料维护与可观测性 | LLM 后端、后端、QA | 健康度检查、版本管理、反馈样本与评测对比报告。 |
| Phase 3 | 根据真实使用反馈决定是否扩展企业能力 | 产品经理、架构师 | 迭代 PRD；仅在需求被验证后评估权限、部门隔离等能力。 |

## 7. 数据范围提示

本 PRD 仅定义业务对象，不定义数据库、接口或模型实现细节；技术方案由系统架构阶段产出。

| 业务对象 | 最小信息 | 用途 |
| --- | --- | --- |
| 制度文档 | 名称、版本、生效日期、失效日期、适用范围、来源、处理状态 | 判断资料是否可检索以及回答时应采用哪个版本。 |
| 知识片段 | 文本、所属文档、页码/定位 | 支撑检索与原文引用。 |
| 问答记录 | 问题、回答、引用、时间、结果状态 | 支撑演示、评测与问题复盘。 |
| 评测样本 | 测试问题、预期依据、评测结果、失败原因 | 验证和改进回答质量。 |
| 用户反馈（P1） | 有帮助/未解决、补充说明 | 发现未覆盖的高频问题。 |

## 8. 成功指标与风险

### 8.1 MVP 成功指标

| 指标 | Phase 1 目标 | 说明 |
| --- | --- | --- |
| 资料可用性 | 至少 3 份制度 PDF 成功进入知识库 | 验证考勤、请假、报销资料到检索的链路。 |
| 检索召回表现 | 在固定测试集上记录 Recall@K，并与纯向量检索基线比较 | 衡量关键依据能否进入候选结果；目标值由首轮基线后冻结。 |
| 回答忠实度 | 使用 RAGAS 或等价规则评测，并结合人工抽检 | 衡量答案是否得到检索依据支持；目标值由首轮基线后冻结。 |
| 引用正确率 | 正常回答的引用均能定位到支持该结论的原文 | 防止“有引用但引用不相关”。 |
| 无答案拒答率 | 无答案测试问题应拒绝编造并提示未找到依据 | 验证知识边界与幻觉控制。 |
| 核心任务完成 | 至少 3 名目标用户各完成 1 次查询 | 验证基本可用性，而非模拟点击量。 |
| 失败样本沉淀 | 每次评测保留失败问题及原因 | 验证项目具备迭代入口。 |
| 交付展示证据 | Demo、评测报告、失败案例和演示素材均可复核 | 证明项目不是仅停留在文档或课程代码层面。 |

### 8.2 主要风险与应对

| 风险 | 影响 | 应对策略 |
| --- | --- | --- |
| 制度资料质量差或扫描件不可读 | 解析与引用不可用 | v1 优先选用可解析 PDF；将扫描件/OCR 质量作为单独风险记录。 |
| 检索内容不相关 | 回答看似合理但不可信 | 通过基线对比、检索召回、回答忠实度与失败样本评测验证改进，不以“模型能回答”作为通过标准。 |
| 模型幻觉 | 员工误解制度 | 明确证据不足时拒答，展示原文依据与人工确认提示。 |
| 制度版本或适用范围混乱 | 引用过期或不适用规则 | 保留版本、生效日期和适用范围；冲突时并列展示并转人工确认。 |
| 项目范围膨胀 | 项目长期无法完成 | Phase 1 只交付三项 P0；其他能力必须在 MVP 验收后再排期。 |

## 9. 交接说明

本 PRD 已冻结 Phase 1 的产品边界：**制度文档导入、带引用问答、质量验证**。下一步由系统架构阶段产出与本 PRD 对应的技术 SPEC、流程 DAG、接口边界与测试计划；实现与简历描述必须以真实测试和演示证据为准，在 Phase 1 验收通过前不启动反馈系统、权限、审批流、复杂协作或多部门隔离开发。
